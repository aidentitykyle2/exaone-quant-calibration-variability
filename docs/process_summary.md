# 실험 전체 프로세스 정리 (논문 작성 근거용)

이 문서는 가상환경 구성부터 현재까지 진행된 모든 단계를, 논문의 어느 장(章)에 어떤 근거로 쓰이는지와 함께 정리한 것이다.

---

## 1단계. 연구 설계 (→ 논문 1장 서론, 2장 관련연구)

- 연구 목적 확정: "한국어 LLM 서빙을 위한 4비트 양자화 기법 선택 가이드"
- 대상 기법: AWQ, GPTQ, QuaRot(회전 기반), SpinQuant(학습된 회전)로 출발
- 대상 모델: EXAONE 3.5-7.8B-Instruct, (Solar-10.7B 확장은 향후 검토)
- 이후 논의를 거쳐 SpinQuant는 **범위에서 제외**(3단계에서 사유 확정), 방법론의 프레이밍을 "완전한 기법 재현"에서 **"현재 프로덕션 서빙 스택에서 실제 배포 가능한 W4A16 기법 비교"**로 조정 — 이 조정 자체가 1장 연구 문제 설정의 핵심 논거가 된다.

## 2단계. 환경 구성 (→ 3장 실험 설계 "실행 환경" 절, 부록 재현성 기록)

이 단계가 가장 많은 시행착오를 거쳤고, **그 시행착오 자체가 방법론적 근거로 전환된다.**

- AutoAWQ(2025-05 유지보수 종료), AutoGPTQ(2025-04 아카이브)를 발견 → llmcompressor 하나로 통일하는 방향 전환
- PyTorch가 2.14.0을 끝으로 CUDA 12.x(드라이버 상한) 지원 종료, 2.15부터 CUDA 13 전용 전환이라는 사실 확인 → 이게 이후 모든 버전 충돌의 근본 원인이었음을 특정
- vLLM 각 버전이 요구하는 정확한 torch 버전을 리졸버 오류 메시지로 역추적(0.9.x→2.6.0, 0.11.1~0.13.0→2.9.0, 0.17.0~0.19.1→2.10.0 ...)
- llmcompressor가 요구하는 transformers 상한(4.57.6)과 vLLM 최신판이 요구하는 하한(5.5.3+) 사이에 교집합이 없다는 것을 확인 → vLLM을 상한 버전대(0.19.0)로 낮춰 교집합 확보
- **최종 확정 조합**: `torch==2.10.0+cu126`, `vllm==0.19.0`, `llmcompressor==0.10.0.3`, `compressed-tensors==0.14.0.1`, `transformers==4.57.6`
- 이 조합은 이 대화 내에서 실제 의존성 리졸버로 검증됨(가상 테스트 환경) + 서버에서 실치 설치 성공으로 이중 확인됨

**논문 반영**: 이 과정 전체를 "재현성 확보를 위한 라이브러리 버전 확정 과정"으로 요약해 3장에 명시하고, 왜 이 조합이어야 하는지(CUDA 세대 전환 시점과 겹친 특수성)를 밝히면 재현성 측면에서 강점이 된다.

## 3단계. 모델 특이사항 확인 및 코드 구현 (→ 3장 "아키텍처별 구현 세부사항")

- EXAONE 3.5 저장소가 2026-02-06 커밋에서 config.json을 transformers v5 방식(rope_parameters)으로 갱신 → 우리 환경(v4계열)과 충돌 → **리비전 고정**(`0ff6b5ec...`, 2024-12-11)으로 해결
- EXAONE의 실제 모듈 구조(`transformer.h.N.ln_1/ln_2`, `attn.attention.{q,k,v}_proj`, `mlp.c_fc_0/c_fc_1/c_proj`)를 직접 확인 → llmcompressor의 아키텍처 자동 인식(Llama 전제)이 실패한다는 것을 확인
- **AWQ 매핑**: forward 코드 확인(`output=c_proj(act(c_fc_0(x))*c_fc_1(x))`)으로 활성화 경로(c_fc_0)와 선형 경로(c_fc_1)를 구분해 매핑 구성. GQA(32Q/8KV heads)로 인한 `v_proj→out_proj` 차원 불일치(1024 vs 4096) 확인 후 해당 매핑 제외
- **QuaRot(SpinQuantModifier) 매핑**: `mappings`/`norm_mappings` 생성자 인자가 라이브러리 버그로 무시됨을 소스 코드로 확인 → `transform_config`를 직접 구성하는 방식으로 우회
- **R3 제외**: EXAONE 고정 리비전이 AttentionInterface 미지원(기술적 제약) + W4A16에서는 활성화 양자화가 없어 R3 자체가 수학적 항등연산(방법론적 근거) — 이중 근거
- **R4 제외**: intermediate_size가 2의 거듭제곱이 아니라 Hadamard 행렬 구성 불가(기술적 제약) + 역시 W4A16에서 항등연산(방법론적 근거)
- **SpinQuant(learnable=True) 자체가 llmcompressor==0.10.0.3에 미구현**임을 소스 코드로 확인 → 연구 범위에서 최종 제외, 향후 연구로 이관
- 코드 구현: 단계 분리 실행(OOM 방지), pynvml 기반 정확한 GPU 메모리 측정(vLLM이 서브프로세스에서 동작해 torch.cuda API가 무효함을 실측 확인 후 교체), vLLM 로그 자동 파싱, tokenizer 일관성 자동 검증 — 모두 실측 오류를 겪은 뒤 도입한 안전장치

**논문 반영**: 이 단계의 모든 "제외 결정"은 우연한 타협이 아니라 코드/실측 근거가 있는 결정이므로, 3장에서 각각을 "왜 뺐는지"와 함께 명시하면 심사 방어력이 커진다.

## 4단계. 양자화 실행 (→ 5장 결과 "효율성" 절 원자료)

BF16, AWQ, GPTQ, QuaRot(R1+R2) 네 가지 모두 완료.

| 기법 | model_loading | kv_cache_tokens | max_concurrency | 처리량 |
|---|---|---|---|---|
| BF16 | 14.57 GiB | 398,016 | 194.34x | ~1270 tok/s |
| AWQ | 4.93 GiB | 477,248 | 233.03x | ~1650 tok/s |
| GPTQ | 4.93 GiB | 477,728 | 233.27x | ~1690 tok/s |
| QuaRot | 4.93 GiB | 477,728 | 233.27x | ~1080 tok/s |

**논문 반영**: QuaRot이 유일하게 BF16보다도 느린 처리량을 보인 것은 6장(논의)의 흥미로운 소재다 — 회전된 가중치를 다루는 vLLM 커널(MacheteLinearKernel)이 AWQ/GPTQ 전용 최적화만큼 성숙하지 않을 가능성을 시사하며, 최근 조사한 "커널이 알고리즘보다 처리량을 좌우한다"는 2026년 업계 트렌드와 직접 연결되는 지점이다.

## 5단계. 정확도 평가 (→ 5장 결과 "정확도" 절, 진행 중)

- 태스크 확정: KMMLU, KoBEST(BoolQ/COPA/WiC/HellaSwag/SentiNeg), HAE-RAE — `TaskManager`로 실존 확인 완료
- 평가 엔진을 `--model hf`에서 `--model vllm`으로 전환(KMMLU가 수백 개 서브태스크를 묶은 대형 집계 태스크라 속도 문제로 전환) — vLLM V1의 서브프로세스 구조 때문에 로그우도 계산이 초반엔 느리다가 배치가 채워지며 급격히 빨라지는 패턴을 실측으로 확인(4it/s → 76it/s)
- **BF16 완료**: KMMLU 0.4555, KoBEST BoolQ 0.9053, COPA 0.848, WiC 0.677, HellaSwag 0.59, SentiNeg 0.9824, HAE-RAE 0.7663
- 중간에 KMMLU 데이터셋 원격 검증 과정에서 일시적 404 발생 → 로컬 캐시는 멀쩡함을 확인 → `HF_HUB_OFFLINE=1`로 우회
- **현재**: AWQ, GPTQ, QuaRot 평가를 `nohup` 백그라운드로 재개, 진행 중

## 6단계 (진행 중 → 곧 도달). 결과 취합

## 향후 논문 작성 단계

### 7단계. 5장(실험 결과) 작성
- 6단계 취합 결과를 표/그래프로 정리
- 정확도(4개 기법 × 7개 태스크)와 효율성(4단계 표) 두 축을 나란히 제시
- 가능하면 정확도 손실 대비 효율성 이득의 산점도(Pareto frontier)로 시각화

### 8단계. 6장(논의) 작성 — 가설 대조표 채우기
지난 논의에서 세운 가설을 실측치와 대조:

| 가설 | 채택/기각 | 근거 |
|---|---|---|
| H1: rotation(QuaRot) > AWQ/GPTQ (정확도) | (5장 수치로 판정) | |
| RQ: 한국어 환경에서 격차 방향 | (탐색적 서술) | |
| (신규) 커널이 알고리즘보다 처리량을 좌우한다 | QuaRot 처리량 실측으로 뒷받침 | MacheteLinearKernel vs Marlin 커널 가능성 |

- R3/R4 제외, SpinQuant 미구현이라는 제약을 "한계"가 아니라 "현재 프로덕션 생태계의 실제 경계"로 프레이밍(4단계 방법론 재조정 근거 그대로 사용)

### 9단계. 7장(실용 가이드) 작성
- 시나리오별 권장 기법(정확도 우선/메모리 제약/지연시간 민감)을 5장 수치 기반으로 확정
- H100 등 데이터센터급 GPU에서는 FP8이 업계 기본값이라는 조사 결과를 언급해, 본 연구의 W4A16 비교가 "VRAM이 더 부족한 상황"을 겨냥한 것임을 명시

### 10단계. 8장(결론) 및 초록 최종화
- `abstract.txt`, 초록의 "제공하고자 한다"를 실험 완료 후 "제시한다"로 수정
- 향후 연구: SpinQuant(learnable) 지원 라이브러리 등장 시 재검토, EXAONE 4.0(공식 transformers 통합, 원격코드 문제 회피 가능성) 확장 — `exaone4_handoff.md` 내용을 그대로 근거로 사용
- Solar-10.7B 확장 여부를 이 시점에 최종 결정(시간 허용 시 진행, 아니면 향후 연구로 명시)

### 11단계. 전체 검토
- 3장에 서술한 모든 "제외 결정"이 5~6장 수치와 모순 없이 이어지는지 확인
- 재현성 부록(라이브러리 버전, 리비전 해시, 하이퍼파라미터)을 `results.json`의 `environment` 필드에서 그대로 옮겨 완성
